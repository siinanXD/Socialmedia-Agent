# Architecture (stack decided 27.10.2026, not yet implemented)

## Components
- API: no separate API service. Next.js (Vercel) server code and Supabase (Auth, PostgREST with RLS, Edge Functions) serve the job contract below.
- Worker: Python 3.12 worker in `worker/` consuming a Supabase queue for ingest/analysis/render; retries, idempotency keys, job progress, cancellation and cost accounting.
- Media: FFmpeg/ffprobe baseline; optional scene detector, ASR and embeddings behind versioned adapters; CPU fallback; GPU optional.
- Storage: separate private Supabase Storage bucket(s) in the same project for creator-isolated immutable originals and derived media, signed URLs, quotas, retention and deletion policies. Do not store video blobs in PostgreSQL.
- Persistence: reuse existing Supabase project `Content-Agent-Lernapp` (project ref `zxielkiwgcgxyudqemjb`) as requested, with a dedicated `social_media` PostgreSQL schema, app-scoped DB privileges, tenant-aware RLS where exposed, separate migration ownership and auditable job/post/event history. Do not modify existing Content Agent / Leitstand tables or schemas without impact assessment.

## Trust boundaries
Creator user -> authenticated API -> scoped storage/DB -> worker -> artifacts -> human approval -> publishing adapter.
Leitstand -> signed/versioned task API with scoped service identity. No direct database superuser access or shared provider tokens.

## Contract sketch
POST /v1/jobs (Idempotency-Key) -> {job_id,status}; GET /v1/jobs/{id} -> {status,progress,artifacts,error}; POST /v1/jobs/{id}/cancel; POST /v1/artifacts/{id}/approve; GET /v1/health.
Job input: creator_id, asset_ids, output_formats, language, target_platforms, budget_cap. Outputs: original asset IDs, clip start/end timestamps, confidence, rationale, versioned pipeline, URLs with expiry, costs, rights/approval state. Implemented as Supabase tables/RPCs with RLS (signed Edge Function for Leitstand), not as FastAPI routes. The HTTP paths above are a proposed contract, not existing endpoints.

Worker-Vertrag (umgesetzt, SIN-1379; Schema `social_media`, nur `service_role`):
- `claim_next_job(worker_id text, lease_seconds int, kinds text[] default null) -> setof jobs`: höchstens ein Job. Gewählt wird der älteste `queued` mit `run_after <= now()` und ohne `cancel_requested`, per `FOR UPDATE SKIP LOCKED`; er wechselt auf `running` mit Lease, `attempts + 1`. Vorher holt die Funktion abgelaufene Leases zurück: mit Abbruchwunsch → `cancelled`, mit freien Versuchen → `queued`, sonst `failed` mit Grund. Wartende Jobs mit Abbruchwunsch werden `cancelled`. `lease_seconds` liegt zwischen 1 und 3600, sonst 22023.
- `heartbeat_job(job_id uuid, worker_id text, progress int, lease_seconds int default 300) -> boolean`: setzt den Fortschritt und verlängert die Lease. `true` heißt: Der Nutzer will abbrechen, der Job ist jetzt `cancelled`, der Worker hört auf.
- `complete_job(job_id uuid, worker_id text, result jsonb) -> jobs`: `succeeded`, `progress = 100`, `result` gespeichert. Idempotent: ein schon erfolgreicher Job bleibt unverändert.
- `fail_job(job_id uuid, worker_id text, error text, retry boolean default true) -> jobs`: Mit `retry` und freien Versuchen geht der Job zurück auf `queued`, mit Backoff 30 s · 2^(Versuch−1), höchstens 1 h. Sonst wird er `failed`; ein Abbruchwunsch macht ihn `cancelled`. Der Fehlertext wird auf 2000 Zeichen gekürzt. Idempotent bei `failed`.
- Gemeinsam: `heartbeat_job`, `complete_job` und `fail_job` verlangen einen laufenden Job, dessen Lease dem `worker_id` gehört; sonst kommt 55P03 (`lock_not_available`).

## Delivery
Develop standalone first. Leitstand integration only after independent smoke tests and auth review. No direct webhook that triggers publishing without approval.
